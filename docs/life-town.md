# 生活小镇 — 产品世界观决定记录

**决定日期**：2026-09-09。**状态**：方向已锁定并已有 UI 表达层；
当前实现状态以 `PROJECT_STATE.md` 为准。本决定不要求改 canonical schema、
包名或内部 energy 命名。

## 决定内容

项目原先暂定名 **Life Energy**，核心语义是「收入=能量输入、支出=能量
消耗、结余=储能、投资=能量外输」。现上层产品概念调整为**生活小镇**：

- 生活小镇**不是**「一个消费分类对应一栋建筑」，而是一个有生活气息的
  微缩社区：居民楼、便利店、咖啡店、公交站、街道、河道、施工区等元素
  表达真实生活状态。
- 底层账本与财务事实架构**保持不变**：
  Raw Evidence → Canonical Ledger → Derived Interpretation。
- **Life Energy 降级为内部派生语义的名字**：收入/消费/结余/投资外输的
  计算逻辑、`energy/` 模块、`energy_type` 枚举、CLI 命令、schema 全部
  保持不变——它不再是产品名称或主要 UI 世界观。

## 世界观分工

| 元素 | 表达 | 数据来源 |
|---|---|---|
| 生活小镇 | 「生活」：日常现金流的状态、活跃度、建设进度 | canonical ledger + 派生层 |
| 海獭控股（Otter Holdings） | 「资本增长」：投资外输连接到的外部资本世界 | ENERGY_EXPORT 事实 + provenance |

财务数据驱动生活小镇的整体状态、活跃度、建设进度和对外投资连接；
小镇自身**不产生任何财务事实**，所有状态可追溯回 canonical 数据。

## 后续开发原则（硬约束）

1. **不因视觉概念调整修改底层 canonical transaction 事实模型**。
   事实层变更只能来自财务事实本身的需要，且必须走增量迁移
   （data-invariants #17）。
2. **不把建筑与消费分类做一一对应**。分类（FOOD/HOUSING/TRANSPORT/…）
   是解释层的规则输入；小镇元素是表达层概念。两者之间不建映射表、
   不建 schema 关联——表达层自己决定小镇如何呈现。
3. **财务数据驱动小镇**。小镇的任何状态变化都必须能回答「为什么」
   （对应哪些交易/周期汇总），provenance 精神延伸到 UI。
4. **生活小镇表达「生活」，海獭控股表达「资本增长」**。两者共享
   ENERGY_EXPORT 事实作为输入素材，但语义分工不同，不混用。
5. **UI 不反向定义账本**。Living Town 表达层已经存在，但账本、导入、
   分类、转账识别、退款、投资外输等底层能力仍独立演进；视觉概念不得
   反向修改财务事实。

## 命名政策

- 仓库名、包名（`life_energy`）、CLI 名（`life-energy`）、模块名
  （`energy/`）、schema、CLI 命令、data-invariants **全部不改**。
- 对上（产品名、未来 UI、面向用户的叙述）用「生活小镇」。
- 「能量 / energy」词汇保留在内部派生层；未来 UI 表达时翻译成小镇
  语言，不外泄实现术语（如 UI 上不出现「ENERGY_EXPORT」字样）。
